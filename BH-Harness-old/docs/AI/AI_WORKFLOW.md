# Breach One AI workflow

Package: B1-CODEX-OPS | Version: 0.1.0 | Prepared: 2026-09-08
Status: CANDIDATE workflow; effective only after human adoption.

## Default loop and division of responsibility

Design Chat frames the player/developer problem, compares alternatives, reviews technical risks,
and resolves the question gate with the human. Only the human approves a system and then its
milestone. Once those approvals exist, compile a coding package without redesign. The human
transfers it to Codex. Codex inspects the actual repository, implements the authorized scope,
validates it, and returns evidence. Verification Review assesses the result; the human closes it.
M prepares canonical publication deltas. No automatic synchronization is assumed. [B1-METHOD, B1-K12]

This instruction-pack assignment creates workflow documents and templates. It does not create
an approved game system, milestone roadmap, prototype authorization, or live repository change.

## Choose the smallest legitimate task

| Task | Required authority | Permitted outcome |
|---|---|---|
| Consultation or archive/document review | Current request | Advice, findings, candidate documents; no source execution by implication |
| Read-only repository audit | Current request and read access | Evidence packet, actual paths/versions, gaps; no editor launch or source writes |
| Small local fix | Explicit bounded request with clear behavior and permitted actions | Fix plus proportional validation; no full L3 paperwork unless risk requires it |
| System/milestone implementation | Approved system + approved milestone + current contracts and validation | Only that milestone; do not request a second plan approval |
| Experimental prototype | Approved experimental system/milestone OR explicit human expedited exception | Named variants and test instrumentation only; not production adoption |
| Focused iteration | Original approved package plus authorized correction scope | Resolve remaining criteria without unrelated redesign |
| Closure/publication | Explicit human acceptance and publication scope | Record actual acceptance; update only delegated shared records |

A generic "implement this idea" does not bypass required L2/L3 decisions. A truly small fix must
not be inflated into an approval ceremony. If classification is uncertain, state the material risk,
not a long checklist, and ask only the question that changes the work.

## Separate status dimensions

Design/milestone specification: DRAFT → CANDIDATE → QUESTION GATE → READY FOR APPROVAL → APPROVED.
Approval remains tied to a recorded human decision, scope, and revision.

Package compilation: DRAFT / BLOCKED / COMPILED FROM APPROVED INPUTS. Compilation does not add approval.
Implementation: NOT STARTED / IN PROGRESS / BLOCKED / READY FOR REVIEW.
Review recommendation: READY TO CLOSE / PASS WITH DEFERRED ITEMS / ITERATION REQUIRED /
DESIGN CHANGE REQUIRED / BLOCKED.
Human closure: PENDING / ACCEPTED / DECLINED. Only accepted closure permits COMPLETE.
Research disposition: RECEIVED / REVISION REQUESTED / ACCEPTED AS EVIDENCE / ARCHIVED.
None of these substitutes for another dimension.

## Codex cycle

Preflight the package and checkout. Inspect the owning paths before edits. Make coherent,
reviewable slices. Run focused checks during work. At the final candidate revision, review scope
and contracts, execute all required final gates, and produce an AC evidence matrix. Preserve
failed/skipped/missing evidence and remaining human checks. Update authorized work/completion
records; propose shared-state changes separately. [B1-K09, B1-K12]

If a locked decision must change, stop the affected work, record the smallest conflict and
alternatives, and return it to Design/human authority. A new helper class inside an approved
boundary usually needs no design question; a new network owner or checkpoint rule does.

## Bounded review coverage

Architecture review checks ownership, lifecycle, persistence, compatibility, scale and dependencies.
Adversarial review seeks concrete counterexamples. Neither substitutes for execution or player testing.
For this pack, runtime discovery/behavior checks remain NOT RUN until exercised in the actual Codex host.
