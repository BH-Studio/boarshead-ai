# Unity, middleware, and content safety

Package: B1-CODEX-OPS | Version: 0.1.0 | Prepared: 2026-09-08
Status: CANDIDATE workflow; effective only after human adoption.

## Version evidence before API use

Read actual Unity patch, package lock, asmdefs, vendor metadata and integration versions. Consult
primary documentation matching those versions when needed; record mismatches. Unity 6.3 LTS is
the supplied project baseline, not a claim about what is installed. Do not lift Unity 6000.5.7f1
from the Galaxy archive. An import success does not establish gameplay, networking or performance
compatibility. [B1-STACK; B1-CONTEXT]

These are boundaries to inspect, not an instruction to implement every row. Opsive's current
integration documentation describes the intent/controller division; it does not prove the
uninspected project's BD Pro/UCC/A* combination works. [B1-STACK §3; EXT-OPSIVE]

## Unity asset and serialization controls

Preserve asset/.meta pairs and existing GUIDs when moving or editing assets. Missing metadata
can break serialized references. New Unity assets require their valid metadata generated by an
authorized Editor/import workflow or an established inspected project tool; do not fabricate
GUIDs to disguise a missing import step. [EXT-UNITY-META]

Treat serialized field/type/namespace/assembly changes as migration-sensitive. Inventory affected
prefabs, scenes, definitions and save fixtures; use version-appropriate migration support where
approved. Do not bulk-reserialize a code-only task. Keep runtime/editor/test assembly boundaries
valid; keep platform-specific and presentation dependencies on their intended side.

Shared ScriptableObject assets are configuration/authoring sources unless a contract explicitly
says otherwise. Distinguish definitions, runtime state, campaign state, player knowledge and
rebuildable presentation caches. Ensure reset/retry/scene unload does not persist test mutations.
Pair event registration and cleanup; test re-enable, scene restart, pool reuse and domain-reload
settings where applicable. Pooling is a measured implementation choice, not a new mandatory framework.

## Content and Editor deliverables

A script is not a complete feature when its scene/prefab/configuration is missing. Each applicable
package supplies scene purpose, source prefab and component ownership, inspector references,
input/animation bindings, collision/layer assumptions, authoring validation, reset/rebuild steps
and manual acceptance. Reuse existing tooling before adding custom editors. For any builder,
define idempotency, deterministic identity where needed, undo/backups, safe write roots and rerun
behavior. Generated content must not overwrite hand-authored work silently.

Prefer supported integrations and project-owned adapters only at real policy/testing/replacement
boundaries. Do not import old and new Behavior Designer generations, multiple motors, inventory
systems or entire VFX libraries merely because they are owned. Review vendor changes with exit
cost, upgrade risk and license constraints. A second-consumer claim requires the named actual
consumer test; Ashfall Raiders is a candidate, not proof already achieved. [B1-K08; B1-STACK]

## Performance and build effects

Inspect allocations, repeated searches, update frequency, AI/path requests, event fan-out,
particle/audio concurrency and retained state where changed. Use workload and frame-time evidence
rather than automatic ECS/Jobs/Burst/Addressables adoption. Run relevant player/target tests when
serialization, rendering, stripping, input, platform APIs or middleware change. No Xbox
certification or mobile support is implied by a Windows build.
